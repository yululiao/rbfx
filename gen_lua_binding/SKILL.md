# gen-lua-binding

Produce, from a C++ usage example under `rbfx/Source/Samples/`, (a) the matching
additions to the hand-written sol3 binding translation units and (b) a faithful Lua
port under `rbfx/Source/LuaSamples/`, then prove nothing regressed. The bindings and
samples in this repo are AI-generated by scanning C++ — this skill is the contract that
generation must follow so the API surface stays parseable, typeable, and green.

## Input (argument)

The skill is parameterized by a target sample. Invoke as `/gen-lua-binding <target>` where
`<target>` is any of these forms; resolve all of them to a `Source/Samples/<NN_Name>` directory:

- full/relative path: `rbfx/Source/Samples/01_HelloWorld` or `Source/Samples/01_HelloWorld`
- bare sample name: `01_HelloWorld` (→ `Source/Samples/01_HelloWorld`)

From that one directory:
- Read its C++ (the `*.cpp` files) — that is the authoritative list of engine types, methods,
  enums, events and resources to (a) ensure are bound and (b) port.
- The Lua port lands at `Source/LuaSamples/<NN_Name>/main.lua` (same `NN_Name`), and the
  incremental smoke targets `-Only <NN_Name>`.

If no argument is given, use the sample the user names in their request. If the target is
missing or ambiguous (several samples cited, or none), ask which one — never sweep the whole
Samples tree unprompted. Scope is exactly that one sample: touch only the binding TUs/entries
it needs, and verify with parity + the `-Only <NN_Name>` smoke (steps 6-8), not the full suite.

## Non-negotiable model

- **Non-invasive**: never touch engine code (`Source/Urho3D/**`). All Lua knowledge lives
  in the bolt-on TUs under `Source/LuaScript` (runtime) and `Source/Editor/EditorLuaScript` (editor).
- **Source-parsed docs**: the LuaLS stubs (`engine.d.lua` / `editor.d.lua`) are produced by
  `Source/Tools/ApiDocGen/generate_api_docs.py`, which reads the *registration source text*
  by token. Every rule below exists to keep that parse correct.

## Subsystem → TU map (edit the right file)

`Source/LuaScript/` holds one TU per subsystem, registered in this order
(see `LuaVM::RegisterEngineBindings`):
`LuaMathBindings` · `LuaCoreBindings` · `LuaNodeBindings` · `LuaResourceBindings` ·
`LuaGraphicsBindings` · `LuaInputBindings` · `LuaUIBindings` · `LuaPhysicsBindings` ·
`LuaUrho2DBindings` · `LuaPhysics2DBindings` · `LuaAudioBindings` · `LuaNavigationBindings` ·
`LuaNetworkBindings`. Editor-only API → `Source/Editor/EditorLuaScript`. Pick the TU by the
owning subsystem; if the type is new, add a `new_usertype` in the subsystem TU and wire a
`Register<Sub>Bindings` call if a whole new module is being onboarded.

## Workflow

Copy and track this checklist:

```
- [ ] 1. Read the target sample's C++ (the argument's directory); list every engine type + method it touches
- [ ] 2. For each type/method, check if already bound (grep the TU); note the gaps
- [ ] 3. Add bindings obeying the Authoring Contract below
- [ ] 4. If an enum is needed by the sample but has no name table, add one (int table only)
- [ ] 5. Port the C++ demo to Lua, mirroring idioms from the CLOSEST existing LuaSample
- [ ] 6. Compile the binding lib (0 errors)
- [ ] 7. Run the two generator bats, then check_api_docs parity (must be green)
- [ ] 8. Relink the runner (re-stages samples), then smoke ONLY the samples you added/changed
       (run_samples.ps1 -Only <name>). New sample dirs auto-join the full suite via dir-scan;
       running the FULL suite is a human call via run_all_samples.bat, NOT this skill.
```

### Steps 6-8 are the per-batch gate (incremental smoke only)

Batch all binding+sample edits, then verify once. The skill's smoke is **incremental only**
(`run_samples.ps1 -Only` the samples you just touched) so a batch is confirmed in seconds,
not minutes. There is no separate sample list to maintain: `run_samples.ps1` scans
`Source/LuaSamples/*/main.lua` on every run, so a newly ported sample automatically joins the
full suite the moment its directory exists. When the FULL suite should run is a human
decision -- do it by double-clicking `run_all_samples.bat` at the repo root.

## Binding Authoring Contract (HARD rules)

Violation of rule 1 or 2 silently corrupts the code hints; rule 3 is the top source of
runtime breakage; rules 4-6 prevent capability regressions.

1. **Registration keys must be literal at the call site.** The parser only recognizes these
   shapes; a helper/builder that swallows the string key drops the member from the docs:
   - `lua.new_usertype<T>("Name", "Key", <value>, "Key2", <value>, ...)`
   - `lua.set_function("name", <value>)` / `luaState_->set_function(...)`
   - `lua.create_named_table("X")` (then `X["MEMBER"] = <value>`)
   - `lua["Name"] = <value>`
2. **Getters / annotated returns keep an explicit lambda with a trailing `-> Type`.**
   `extract_return_base` derives `---@return` / `---@type` from the first `->` in the bound
   value token stream. `return [](Node* n) -> Vector3 { ... }` keeps the annotation;
   a bare member pointer or a helper wrapper has no `->` and the return hint silently vanishes.
3. **`NullChecked(&T::M)` is for void / side-effect members ONLY** (see
   `Source/LuaScript/LuaBindHelpers.h`). Do NOT wrap a member that is:
   - **overloaded** (e.g. `RemoveChild`, `SetEnabled`, `Remove`) → `&T::M` is ambiguous → C2672/C2784;
   - **has default arguments** (e.g. `RotateAround`, `Pitch/Yaw/Roll` with `TransformSpace space = ...`)
     → the helper absorbs the default into `Args...`, silently raising Lua arity (compiles,
     parity-clean, breaks only at runtime);
   - **returns a value** the docs annotate, or returns a raw pointer that must become a `SharedPtr`.
   A plain `&T::M` is already the simplest form — only reach for `NullChecked` when the old
   code was a `if (self) self->M(...)` guard lambda you are collapsing 1:1.
4. **Enums are integer constant tables, never `sol::enum_`.** ~31 tables already exist
   (`TS`, `LIGHT`, `FILTER`, `MM`, `KEY`, `VET`, ...). Registering a typed enum makes sol2
   reject the integer arguments and the `==` comparisons that every existing site uses. To
   expose a previously-magic-number enum that HAS a bound consumer, add a literal table, e.g.
   `sol::table cull = lua.create_named_table("CULL"); cull["NONE"] = CULL_NONE;` …
5. **Object types returned to Lua need `RegisterLuaObjectWrapper<T>()`** so `GetComponent`,
   event payloads, etc. hand back the full usertype (methods/properties) rather than the
   minimal `LuaObjectRef` catch-all.
6. **`LuaToVariant` supported set** (`LuaCoreBindings.cpp`, used by `SetAttribute`/`SetVar`/
   `SetShaderParameter`/`SetKeyFrame`/network maps): bool, string, whole number → `int`
   (32-bit) else `int64`, non-whole → `double`, table `{ type, name }` → `ResourceRef`,
   userdata `Vector2/3/4`, `Quaternion`, `Color`, `IntVector2`, `IntVector3`, `Rect`,
   `LuaObjectRef`, `Object*`. Anything else logs `URHO3D_LOGERROR` and yields `Variant::EMPTY`
   (which CLEARS the attribute) — so never pass an unhandled type through these setters.
7. **Event data is synchronous-only**: a callback receives a `LuaEventData` wrapper that is
   valid only during dispatch; reading it after the callback returns yields `nil` (guarded,
   no longer UB). Never stash the wrapper and read later. Multiple callbacks on the same
   (sender,event) are supported via the fan-out registry — do not assume last-subscriber-wins.
8. **String parameters are `const char*`, never `ea::string`/`const ea::string&`.** A Lua
   string does NOT convert to `ea::string`, so an `ea::string` (or `String`) parameter silently
   fails with `sol: no matching function` at the call site (or, worse, gets swallowed when the
   call sits inside a `protected_function` the engine invokes). Bind inbound strings as
   `const char*` and, if a value must outlive the call (captured by a long-lived callback),
   construct an `ea::string` from it and capture THAT by value. Return strings as `std::string`.
9. **`sol::overload(...)` requires near-exact matches and blocks implicit conversions** — it is
   the top runtime-breakage source after rule 3. Do NOT wrap a single-arity method in
   `sol::overload` just to accept a `ResourceRef` *and* a path string: the overload set rejects
   the Lua string. Prefer one lambda taking `const char*` (rule 8) that constructs what it needs
   (e.g. `[](RmlUIComponent* c, const char* p){ c->SetResource(ea::string(p)); }`).
10. **Object identity is by pointer, and lifetime depends on the representation.** `WrapLuaObject`
    dispatches on the *exact* runtime type: a type with a registered wrapper
    (`RegisterLuaObjectWrapper<T>`) is handed back as a **`SharedPtr<T>` (strong ref — it keeps the
    C++ object alive even after scene removal)**; a type without one falls back to `LuaObjectRef`
    (**`WeakPtr` — safely goes nil but is a different Lua representation of the same object**).
    Add pointer-based `sol::meta_function::equal_to` to every object usertype so `==` compares the
    underlying pointer, not the userdata. **This vendored sol3 has no `meta_function::hash`**, and a
    raw `"__hash"` string key lands under `__index` (invisible to the VM's key-hashing), so a
    userdata's *hash* cannot be customised.
    **A global identity cache now lives in `WrapLuaObject`** (`LuaCoreBindings.cpp`): a per-state
    **weak-valued** registry table keyed by the `Object*` address maps each object to the ONE wrapper
    Lua value handed out for it, so repeated wraps of the same live object return the *same* userdata
    — `rawequal` holds and the wrapper is a stable table key. It never leaks: weak values mean an
    entry vanishes once Lua drops the wrapper; the strong `SharedPtr` of registered wrappers guarantees
    a cache hit is the same live object, and the `LuaObjectRef` fallback re-validates `Get()==object`
    on a hit to survive address recycling.
    **Scope limit — this cache only covers the `WrapLuaObject` path** (GetChildren/ForEach*/GetComponent/
    event senders/subsystems/Variant PTR/unbound types). Accessors that return a registered `T*`/
    `SharedPtr<T>` *directly* (e.g. `.parent`, `.scene`, `GetChild`, `CreateChild`) are pushed by sol3
    as fresh userdata and BYPASS the cache, so across those two paths `rawequal`/table-key do NOT unify
    (only `==` does, via `equal_to`). Do not assume `rawequal` works between a `.parent` value and a
    `GetChildren()` value of the same node. Prefer `==`, and when a single canonical identity matters,
    key by `obj.id`/a stable field. Routing the direct-push path through the cache is a deeper,
    cross-cutting change and must go through the FULL suite.
11. **Register the FULL `sol::base_classes` chain, and mind TU order.** sol3 upcasts only match the
    bases you declare, so an object usertype must list its whole ancestor chain up to `Object`
    (e.g. `sol::bases<Component, Serializable, Object>`); dropping a link silently breaks
    `Object*`-typed paths (event senders, `GetSubsystem` casts) with no compile error. And the
    `Register<Sub>Bindings` calls in `LuaVM::RegisterEngineBindings` are order-sensitive —
    **Resource must precede Graphics** (Model/Material derive from Resource); a new subsystem that
    binds a type deriving from another TU's type must be registered AFTER that TU. There is no
    auto-derivation from reflection; both invariants are hand-maintained.
12. **A destroyed object reached through `ObjectRef` must report, not silently no-op.** `LuaObjectRef`
    (the generic wrapper for unregistered types) holds a `WeakPtr`, so its userdata outlives the C++
    object; after death `Get()==nullptr` and every attribute read/write used to collapse to a silent
    `nil`/dropped write, hiding "operate on a removed object" bugs. `WrapLuaObject`'s `GetAttribute`/
    `SetAttribute`/`GetAttributes`/`__index`/`__newindex` now call `ReportDeadObjectRef(op)` (a
    non-fatal `URHO3D_LOGERROR`, NOT a thrown exception — the project does not force
    `SOL_ALL_SAFETIES`, so a C++ throw could escape into the engine). Keep liveness probes
    (`Get`/`CastTo`/`GetTypeName`/`to_string`) silent: returning nil/`""`/`<destroyed>` is their
    contract. Two boundaries are deliberate: (a) for **registered** types and direct `T*`/`SharedPtr`
    returns, a null already becomes Lua `nil`, so `nil:Foo()` is *already loud* — the `if (self)`
    guards in those lambdas are unreachable defensive code, do not add error paths there; (b) null
    **arguments** (`node:AddChild(nil)`) are intentionally NOT error-globally — many engine params
    legitimately accept null (`SetStyle(nil)`, `LoadLayout(file, nil)`), so blanket-guarding them
    regresses real usage. Only the dead-self reflection path is guarded.

## Hard cases: unbound subsystems & C++-virtual subclassing

Some samples are NOT a simple "add a method to an existing TU" job. Two shapes recur; both were
proven on `107_HelloRmlUI` (whole RmlUI subsystem unbound + the demo's core is a C++ class that
overrides a virtual). The rule is the same: **enhance the Lua-side binding add-on, never touch the engine.**

- **(A) Brand-new subsystem with zero bindings.** Add a fresh TU
  `Source/LuaScript/Lua<Sub>Bindings.cpp`, define `void Register<Sub>Bindings(sol::state&,
  Context*)`, declare it in `LuaBindings.h` (`RBFXLUA_API`), call it at the end of
  `LuaVM::RegisterEngineBindings`, and add the `.cpp` to `RbfxLuaScript.vcxproj` as a
  `<ClCompile>` with `/bigobj` (the glob does NOT auto-include it). Verify the subsystem's own
  lib (e.g. `RmlUi.lib`) is already linked and its macros reach the TU transitively before
  writing anything — that is the compile-feasibility gate; if it fails, the port is not viable
  and you must say so.
- **(B) The demo subclasses a C++ component and overrides a virtual** (e.g.
  `RmlUIComponent::OnDataModelInitialized()` / `Update()`) driven by C++ callbacks
  (`eastl::function`). Lua cannot override a C++ virtual. Ship a **non-invasive trampoline
  component** in your TU: `class Lua<Sub>Component : public <Sub>Component` with
  `URHO3D_OBJECT`, registered via `AddFactoryReflection` so `Node:CreateComponent("Lua<Sub>Component")`
  works. Override the virtual(s) to look up a Lua **handler table** (`SetHandlers(sol::table)`
  stashing a `lua_State*` + `sol::optional<sol::table>`) and call the matching field
  (`onInit`/`update`), passing `WrapLuaObject(lua, this)`. Adapt the engine's callback types to
  `sol::protected_function` (getter/setter/event) so the script binds its own data model.
  Key hazards proven here:
  - Bind-only-in-a-window APIs (RmlUi `BindDataModel*` succeed only while the model
    constructor is alive, i.e. inside `OnDataModelInitialized`) → fire the Lua `onInit` there.
  - Persistent storage the engine holds as a raw pointer must live at a **stable address**: keep
    it in `ea::map` (red-black tree, nodes never relocate), NOT `ea::unordered_map`/vector.
  - Drive per-frame animation from `app:Update` rather than relying on the component's `Update`
    virtual actually being called — lower risk; still forward `update` in the trampoline as a
    capability.

## C++ → Lua sample porting

- The Lua version must mirror the C++ demo's *structure and behavior*. Read 2-3 existing
  `Source/LuaSamples/<name>/main.lua` that touch the same subsystem and **copy their idioms
  verbatim** (how they get subsystems, load resources, construct math types, subscribe to
  events). Do not invent accessor spellings.
- Mechanical mapping: `obj->Foo(a,b)` → `obj:Foo(a,b)`; PascalCase binding names match the
  engine method names. Math types are constructed by their usertype ctors
  (`Vector3(x,y,z)`, `Quaternion(...)`) — confirm each in the `new_usertype`.
- Use named enum constants (`TS.WORLD`, `LIGHT.SPOT`, `MM.RELATIVE`), not raw ints.
- Use `print()` for console output (the VM redirects `print` into the engine log); there is
  no `__urho_log_info` global.
- Layout: a sample dir has `main.lua` (plus its assets). It is staged at build time into
  `msvc/bin/<Config>/LuaSamples/` by the CMake "Copying Lua sample scripts" step.

## Performance notes (measured on the Release build)

Real per-operation costs from a microbenchmark (vanilla Lua 5.4, sol3, hand-written
bindings). Pure Lua local call = ~35 ns; everything below is the engine-boundary tax.

- **~330 ns** rides on each bound method call (arg check + convert) — a `GetNumChildren()`
  call is ~370–410 ns. Fine for orchestration; matters only inside per-entity per-frame loops.
- **~200–600 ns** is the *allocation* tax, not the call: `Vector3(...)` ctor ~580 ns,
  reading a `.position` (returns a Vector3 userdata) ~600–670 ns, a string getter like
  `GetName()` ~420 ns, writing `.position` ~270 ns. So a Lua statement like
  `node.position = node.position + Vector3(0,dt,0)` costs ~1.5 µs and churns 2–3 short-lived
  userdata. In hot loops cache scalars, avoid re-reading vector properties, and don't build
  throwaway vectors per frame.
- **Enumeration cost is dominated by per-child wrapping (~580 ns each), not the table.**
  `parent:GetChildren()` over 20 children ≈ 17–19 µs. `ForEachChild` was added and is NOT
  faster for a full pass (callback overhead makes it ~30 µs); its value is the **early break**
  (`return false` from the callback) — stopping at the first match is ~2.7 µs, ~7× cheaper
  than `GetChildren`. Use `ForEachChild(... return false)` for "find first", keep `GetChildren`
  when you must visit all, and cache the table when the structure is stable.
- **A global object identity cache now lives in `WrapLuaObject`** (contract rule 10): a per-state
  weak-valued registry table reuses ONE userdata per live object. Measured effect on the Release
  build (GC paused, `parent:GetChildren()` over 20 children): cache-cold re-wrap ≈ 19.6 µs, cache-hot
  (wrappers held) ≈ 15.5 µs — ~20 % cheaper because the ~580 ns re-wrap allocation is skipped on a
  hit; the throwaway path is unchanged within noise (the cache lookup bookkeeping ≈ the saved alloc).
  Its larger win is correctness: `rawequal` and userdata-as-table-key now work for values that come
  through `WrapLuaObject` (GetChildren/GetComponent/event senders/subsystems/unbound types). It does
  NOT cover direct-push accessors (`.parent`, `GetChild`, …) — see rule 10's scope limit.
- FindAttribute (the O(n) dynamic-attribute path) is only reached for **unregistered** types
  (`LuaObjectRef`); registered usertypes use direct property methods and never hit it. It now has
  a StringHash fast path, so an exact-name key costs one hash + integer compares (no alloc).

## Acceptance gate (all three must hold)

- **Compile**: 0 errors on `RbfxLuaScript` and `LuaSamplesRunner`.
- **Parity**: `check_api_docs.ps1` reports OK for BOTH engine and editor stubs.
- **Behavior**: each sample you added/changed PASSES its targeted `-Only` smoke (`FAIL=0`).
  The full `49/49` suite is a separate human decision via `run_all_samples.bat`, not a step in this skill.

## Pitfalls (learned the expensive way)

- **Smoke incrementally, and only in the foreground**: `run_samples.ps1 -Only <name>` finishes
  in seconds and is the skill's default. Never run a smoke from a detached background job -- its
  `Start-Process LuaSamplesRunner.exe` wedges there (no log, no process).
- **Staging**: samples run from the copy under `msvc/bin/<Config>/LuaSamples`, not `Source`.
  Editing `Source/**/main.lua` requires relinking the runner (or copying the file) before the
  smoke reflects it. A fresh full runner relink can newly surface pre-existing source bugs in
  samples that were never staged before.
- **Editor target**: uses its own `--header` and `EditorLuaScript` sources; run
  `gen_editor_lua_api.bat`, not the engine one, for editor-surface drift.
- **Silent-drift trio to re-check after any helper/builder refactor**: missing registration
  keys, lost `-> Type` return annotations, and enum→`sol::enum_` conversions. All three pass
  compile and can pass parity while breaking runtime or hints; the smoke and stub diff are the
  only reliable catchers.
- **No codegen / manifest**: this repo deliberately generates via AI + this contract, not a
  manifest-driven emitter. Do not reintroduce a build-time generator beyond the existing
  `generate_api_docs.py` stub tool.
